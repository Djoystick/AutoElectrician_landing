# Аудит проекта «Автоэлектрик с выездом»

**Направления:** Senior Full-Stack · Security · Product UI/UX · Performance  
**Рекомендуемое имя файла:** `AutoElectrician_Audit.md`  
**Вердикт:** текущую реализацию нельзя считать готовой к безопасной эксплуатации CRM с реальными персональными данными.

## Основание и ограничения аудита

Отчёт основан на предоставленном тексте PDF — 36 страниц исходников. Репозиторий и работающий сайт в этой сессии не загружались, запросы к Supabase и Telegram не выполнялись, опубликованные ключи не проверялись.

Отсюда следуют ограничения:

- Уязвимости кода можно установить статически, но фактическую эксплуатацию и утечку из production подтвердить нельзя.
- Настройки Supabase RLS, Storage, инфраструктуры, Git history и фактический состав зависимостей неизвестны.
- Нет результатов Lighthouse, WebPageTest, RUM, скриншотов и тестов на устройствах. Показатели производительности ниже — **целевые бюджеты, а не измерения**.
- Кириллица в PDF повреждена. Это не доказывает проблем с кодировкой сайта. Переносы внутри идентификаторов и символ перед `mascot.js` также требуют проверки по оригинальным файлам.

В исходниках существуют **два разных backend-приложения**:

| Вариант | Точка входа | Хранилище | Авторизация администратора | Telegram |
|---|---|---|---|---|
| Legacy | `server.js`, запускается через `npm start` | `data/data.json` | Пароль в каждом запросе | Polling |
| Supabase | `api/index.js`, указан в `vercel.json` | Supabase | JWT | Webhook |

Это не просто дублирование: реализации имеют разные контракты и разные уязвимости. Ниже они рассматриваются отдельно.

**Обозначения:**

- **Подтверждено кодом** — опасная конструкция присутствует в предоставленных исходниках.
- **Условный риск** — эксплуатация зависит от окружения, данных или доступности ветки.
- **Требует проверки** — необходимых настроек или артефактов нет.

## 1.2. Секреты, пароли и `data.json`

### SEC-01: раскрытие привилегированных секретов

В предоставленных материалах находятся:

- ключ, обозначенный как `SUPABASE_SERVICE_ROLE_KEY`;
- Telegram Bot Token;
- пароль администратора по умолчанию;
- Telegram-идентификаторы и пример заявки.

Значения секретов в отчёте намеренно не воспроизводятся.

**Последствия:**

- Действующий `service_role` обычно позволяет обходить RLS для операций, доступных этой роли.
- Действующий Bot Token позволяет управлять ботом, в том числе менять webhook и отправлять сообщения от его имени.
- Удаление `.env` из последнего коммита **не отзывает** ключ и не удаляет его из истории, PDF, форков и резервных копий.

### План реагирования

1. Ограничить публичный доступ к CRM/auth/webhook до установки исправлений.
2. Отозвать раскрытый Bot Token через BotFather.
3. Отозвать Supabase-ключ по процедуре для используемого типа ключей. Для legacy JWT-based keys учесть зависимости от проектного JWT secret.
4. Заменить отдельный секрет приложения и отозвать административные и клиентские сессии.
5. Сбросить небезопасные пароли мастеров.
6. Проверить:
   - неизвестных мастеров;
   - изменения Telegram-привязок;
   - webhook URL;
   - изменения контактов, прайса и отзывов;
   - необычные чтения/изменения данных, насколько позволяют логи.
7. Сохранить необходимые свидетельства инцидента в защищённом хранилище.
8. Очистить Git history, CI-артефакты и публичные документы с секретами.
9. Включить secret scanning в CI и pre-commit.

> Supabase URL и publishable/anon key сами по себе не равнозначны серверному секрету. Однако безопасность публичного ключа зависит от корректных RLS и grants.

### Что делать с `data.json`

Для production убрать его как хранилище CRM.

Допустимое применение:

- обезличенные fixtures;
- демоданные;
- локальные тесты;
- экспорт с контролем доступа и шифрованием.

Недопустимо хранить в нём пароли, токены, реальные заявки и фотографии клиентов в репозитории.

При этом `data/data.json` расположен **вне `public`**. По показанному `express.static(PUBLIC_DIR)` нельзя утверждать, что файл напрямую доступен через `/data/data.json`. Реальная подтверждённая утечка legacy происходит через API.

## 1.3. SEC-02: публичная выдача CRM в legacy

В `server.js`:

```js
res.json({ ...data, settings: safeSettings, services: activeServices });
```

Исключение пароля из `settings` не защищает остальные поля `data`.

В ответ попадают, если присутствуют:

- `clients`;
- `requests`;
- телефоны, имена;
- автомобили и история ремонтов;
- Telegram-привязки;
- legacy-коды доступа.

**Исправление:** положительный список разрешённых полей, отдельный публичный DTO.

```js
function publicLandingDto(data) {
  return {
    settings: {
      heroTitle: data.settings.heroTitle,
      heroSubtitle: data.settings.heroSubtitle,
      acceptingRequests: data.settings.acceptingRequests,
    },
    contacts: {
      phone: data.contacts.phone,
      city: data.contacts.city,
      workingHours: data.contacts.workingHours,
      telegram: data.contacts.telegram,
      whatsapp: data.contacts.whatsapp,
    },
    services: data.services
      .filter(service => service.active)
      .map(service => ({
        id: service.id,
        title: service.title,
        description: service.description,
        price: service.price,
        icon: service.icon,
      })),
    reviews: data.reviews.map(review => ({
      id: review.id,
      name: review.name,
      text: review.text,
      image: review.image,
    })),
  };
}
```

Перед этим сами данные должны проходить схему валидации.

В Supabase-версии прямого `...data` уже нет — это улучшение. Но исключение нескольких секретных полей через rest-оператор всё ещё уступает явному DTO: новое чувствительное поле легко случайно сделать публичным.

## 1.4. SEC-03–05: Telegram authentication и повышение привилегий

### Webhook не проверяет отправителя

`POST /api/telegram-webhook`:

- сразу отвечает `200`;
- не проверяет `X-Telegram-Bot-Api-Secret-Token`;
- доверяет `message.from.id` и `message.chat.id`;
- подтверждает magic-сессию по полученному сообщению.

Любой HTTP-клиент может прислать JSON, похожий на Telegram Update. TLS обеспечивает шифрование соединения, но не доказывает, что запрос отправил Telegram.

### Возможная цепочка захвата

По коду возможна следующая последовательность:

1. Получение новой pending magic-сессии.
2. Поступление поддельного webhook-события с чужой Telegram-личностью.
3. Привязка или поиск клиента на основании подставленных идентификаторов.
4. Подтверждение сессии.
5. Получение клиентского токена через polling.
6. Если идентификатор совпадает с привязкой мастера — получение admin JWT через `/api/client/me`.

Это статически установленный опасный поток доверия, а не утверждение, что атака уже происходила.

### Утечка пароля в `/api/client/profile`

В Supabase-версии:

```js
if (master) adminToken = master.password;
```

Возвращается **пароль либо его хеш**, а не токен.

- Plaintext даёт непосредственное знание пароля.
- bcrypt-хеш не становится автоматически допустимым Bearer JWT, но раскрывает материал для офлайн-подбора.
- Такое поле следует удалить, а затронутые пароли — сменить.

### Правильная модель Telegram-входа

- Проверять webhook secret до обработки тела события.
- Разрешать пользовательский вход только из приватных чатов.
- Использовать `from.id` как идентификатор пользователя, а `chat.id` — как адрес доставки, не смешивать их.
- Запретить автоматическое повышение привилегий через клиентский профиль.
- Привязывать Telegram к мастеру только из уже аутентифицированной административной сессии с повторной проверкой/MFA.
- Подтверждение и потребление magic-сессии выполнять атомарно.
- Ограничивать TTL, число попыток и частоту создания.
- Отдельно хранить браузерный секрет завершения входа, не передаваемый в Telegram deep link.
- Явно предупреждать в боте, для какого входа запрошено подтверждение.
- Не считать браузерную привязку полной защитой от социальной инженерии: пересланную ссылку жертва всё равно может ошибочно подтвердить.

### Пример проверки webhook

Ниже — фрагмент целевой архитектуры. `updateSchema` и `webhookInbox` должны быть реализованы отдельно; inbox обязан быть долговечным.

```js
const crypto = require('node:crypto');

const webhookSecret = process.env.TELEGRAM_WEBHOOK_SECRET;
if (!webhookSecret) {
  throw new Error('TELEGRAM_WEBHOOK_SECRET is required');
}

function validWebhookSecret(value) {
  if (typeof value !== 'string') return false;

  const actual = Buffer.from(value);
  const expected = Buffer.from(webhookSecret);

  return actual.length === expected.length
    && crypto.timingSafeEqual(actual, expected);
}

app.post('/api/telegram-webhook', async (req, res, next) => {
  try {
    if (!validWebhookSecret(
      req.get('X-Telegram-Bot-Api-Secret-Token'),
    )) {
      return res.sendStatus(403);
    }

    const parsed = updateSchema.safeParse(req.body);
    if (!parsed.success) return res.sendStatus(400);

    // UNIQUE(update_id); повторная доставка не создаёт вторую задачу.
    await webhookInbox.persistOnce(parsed.data);

    // Подтверждаем только после надёжного сохранения.
    return res.sendStatus(200);
  } catch (error) {
    next(error);
  }
});
```

При регистрации webhook передавать `secret_token`. Делать это отдельной deploy-командой, а не при каждом cold start.

**Почему текущий ранний `200` опасен:** при падении обработки Telegram уже считает событие доставленным. В serverless выполнение после завершения ответа дополнительно ненадёжно.

### Legacy-привязка телефона

В `server.js` обычное сообщение с номером телефона заменяет `telegramChatId` существующего клиента без проверки владения номером.

Это может перенаправить OTP чужого клиента.

**Исправление:** не связывать личности по свободно введённому телефону. Нужен подтверждённый номер либо одноразовая привязка из существующей аутентифицированной сессии.

В `api/index.js` похожая логика присутствует в `setupBotHandlers`, но вызов этой функции в показанном webhook-пути отсутствует. Её нельзя автоматически считать активной в Vercel-версии.

## 1.5. JWT, cookies, brute force и CSRF

### Текущие проблемы JWT

```js
const JWT_SECRET =
  process.env.SUPABASE_SERVICE_ROLE_KEY ||
  process.env.JWT_SECRET ||
  'secret-fallback-key';
```

Проблемы:

1. При наличии Supabase-ключа отдельный `JWT_SECRET` игнорируется.
2. Раскрытие одного секрета компрометирует два контура.
3. Известный fallback допускает подделку токенов при неправильной конфигурации.
4. Admin JWT действует 30 дней.
5. Нет серверного logout/revocation.
6. Нет явной проверки `issuer`, `audience`, разрешённого алгоритма.
7. Проверяется наличие мастера по `username`, но не соответствие `decoded.id` найденной записи.
8. Смена пароля не отзывает уже выданные JWT.

Отсутствие allowlist алгоритмов само по себе не доказывает принятие `alg:none` используемой библиотекой. Однако явная фиксация параметров проверки необходима.

### Рекомендация: непрозрачная серверная сессия

Для небольшого CRM JWT не обязателен.

Предпочтительная схема:

- случайный токен с достаточной энтропией;
- в БД — SHA-256-хеш токена;
- в браузере — `HttpOnly` cookie;
- отдельные клиентские и административные сессии;
- абсолютный и idle timeout;
- ротация после входа и повышения привилегий;
- серверный отзыв при logout, смене пароля и блокировке.

```js
const token = crypto.randomBytes(32).toString('base64url');
const tokenHash = crypto
  .createHash('sha256')
  .update(token)
  .digest('hex');

// Сначала сохранить tokenHash, principal_id, expires_at и тип сессии.
// При ошибке БД cookie не выдавать.

res.cookie('__Host-admin_session', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax',
  path: '/',
  maxAge: 8 * 60 * 60 * 1000,
});
```

Для `__Host-` нельзя задавать `Domain`, обязателен `Path=/` и HTTPS. Локальную разработку организовать через HTTPS либо отдельную dev-конфигурацию.

**Важно:** `HttpOnly` снижает риск кражи токена JavaScript-кодом, но не устраняет XSS — вредоносный скрипт может выполнять действия от имени пользователя.

### Если JWT сохраняется

Минимально:

- отдельный случайный `JWT_SECRET`, без fallback;
- короткий access token;
- `sub`, `iss`, `aud`, `jti`;
- `algorithms: ['HS256']` при проверке;
- refresh rotation и обнаружение повторного использования;
- серверный механизм отзыва;
- роль проверяется по актуальному состоянию аккаунта.

### Пароли

В legacy пароль передаётся на каждом запросе и может храниться plaintext.

В Supabase-версии новые мастера получают bcrypt-хеш, но:

- сохраняется поддержка plaintext;
- миграционный скрипт создаёт мастера с plaintext;
- отсутствует полноценная password policy;
- `compareSync` блокирует event loop.

Рекомендуется Argon2id либо корректно настроенный bcrypt с асинхронным API. Plaintext-ветки удалить после принудительного сброса. Для bcrypt учитывать ограничение длины входа в байтах.

### Brute force

`limiterAdmin` подключён к `/api/auth`, но в legacy можно проверять пароль через другие защищённые endpoints, где `authCheck` повторно сравнивает пароль без такого limiter.

Дополнительно:

- `/admin <password>` в legacy-боте не имеет собственного ограничения;
- пароль отправляется текстом в Telegram;
- обработчик логирования сообщений может записать эту команду в публичные логи.

**Защита:**

- отдельный rate limit на IP;
- отдельный — на нормализованный аккаунт;
- бюджет попыток OTP на конкретный challenge;
- shared store, например Redis, для нескольких инстансов;
- прогрессивная задержка;
- MFA для административных операций;
- аудит успешных и неуспешных входов без секретов.

`trust proxy` нужно настроить под реальную инфраструктуру. Нельзя просто включить `true`: это может позволить подменять клиентский IP.

### CORS и CSRF

В Supabase-версии разрешён любой Origin с `credentials: true`.

Это:

- лишает приложение ожидаемой изоляции origin;
- становится особенно опасным после перехода на cookies;
- не является аутентификацией API.

Сейчас основные полномочия передаются через `Authorization` и `x-client-token`. Браузер не добавляет эти заголовки к чужому сайту автоматически, поэтому классический cookie-CSRF не следует объявлять подтверждённым для всех текущих маршрутов.

При переходе на cookies необходимо:

1. `SameSite=Lax` или более строгая политика, совместимая со входом.
2. Проверка точного `Origin` для небезопасных методов.
3. CSRF-токен, привязанный к сессии.
4. Отказ от изменяющих состояние GET.
5. CORS выключен при same-origin либо содержит точный allowlist.

OAuth требует собственного `state`, независимо от защиты обычных форм.

## 1.6. Supabase RLS и авторизация данных

В PDF нет SQL-схем, миграций RLS, grants и Storage policies. Утверждение «RLS отключён» было бы необоснованным.

Но подтверждено, что backend использует `service_role`, если он задан. В этом режиме RLS не компенсирует ошибки Express-авторизации.

### Рекомендуемое разделение

| Данные | Публичный браузер | Клиент | Мастер | Владелец |
|---|---|---|---|---|
| Опубликованные услуги и отзывы | Чтение DTO | Чтение | Изменение по роли | Изменение |
| Заявки | Создание через API | Свои, если реализовано | Разрешённый рабочий набор | Все |
| Ремонты и фото | Нет | Только свои | По назначению | Все |
| Мастера и права | Нет | Нет | Нет управления ролями | Управление |
| Сессии, OTP, секреты | Нет | Нет прямого доступа | Нет прямого доступа | Через служебные процедуры |

В текущем коде любой мастер может создавать и удалять мастеров. Если бизнес ожидает разные роли, это отсутствие RBAC.

### Пример baseline для закрытых таблиц

```sql
alter table public.clients enable row level security;
alter table public.requests enable row level security;
alter table public.auth_sessions enable row level security;
alter table public.auth_otps enable row level security;
alter table public.auth_magic_links enable row level security;
alter table public.masters enable row level security;
alter table public.settings enable row level security;

revoke all on table
  public.clients,
  public.requests,
  public.auth_sessions,
  public.auth_otps,
  public.auth_magic_links,
  public.masters,
  public.settings
from anon, authenticated;
```

Это пример для архитектуры, где доступ идёт через backend. Перед применением проверить текущие зависимости и существующие политики.

Обязательно отдельно проверить:

- views и функции;
- `SECURITY DEFINER` и `search_path`;
- grants на схемы и последовательности;
- доступ к Storage;
- `EXECUTE` для RPC;
- default privileges для будущих таблиц.

**Не использовать `auth.uid()` механически:** текущие собственные токены из `auth_sessions` не являются Supabase Auth JWT. Чтобы применять RLS по `auth.uid()`, нужна отдельная интеграция с Supabase Auth и связка пользователей.

Долгосрочно обычному API желательно дать более узкую DB-роль. `service_role` оставить для миграций и ограниченных служебных задач.

## 1.7. Валидация заявок, спам и XSS

### Заявки

В обоих backend `POST /api/requests` проверяет только наличие `phone`.

Не проверяются:

- типы и длины;
- корректность номера;
- разрешённые значения;
- частота запросов;
- повторная отправка;
- размер отдельных полей.

`limiterPublic` объявлен, но к этому маршруту не подключён.

### Пример входной схемы

Ниже — пример с Zod, который необходимо добавить в зависимости. `leadLimiter` должен использовать общее хранилище, а `leadService` — надёжное сохранение заявки и outbox.

```js
const { z } = require('zod');

const leadSchema = z.object({
  name: z.string().trim().max(80).default(''),
  phone: z.string()
    .trim()
    .max(32)
    .transform(value => {
      const compact = value.replace(/[\s()-]/g, '');
      return /^8\d{10}$/.test(compact)
        ? `+7${compact.slice(1)}`
        : compact;
    })
    .pipe(z.string().regex(/^\+7\d{10}$/)),
  problem: z.string().trim().max(1500).default(''),
  idempotencyKey: z.string().uuid(),
}).strict();

app.post('/api/requests', leadLimiter, async (req, res, next) => {
  try {
    const parsed = leadSchema.safeParse(req.body);
    if (!parsed.success) {
      return res.status(422).json({
        ok: false,
        error: 'invalid_request',
      });
    }

    const result = await leadService.createOnce(parsed.data);

    return res.status(result.created ? 201 : 200).json({
      ok: true,
      id: result.id,
      status: 'received',
    });
  } catch (error) {
    next(error);
  }
});
```

Это схема для российского номера. Если зона обслуживания предполагает другие страны, использовать соответствующую политику и проверенную библиотеку номеров.

Дополнительно:

- уменьшить JSON body limit для заявки, например до 16–32 КБ;
- добавить honeypot и ограничение повторов;
- CAPTCHA включать по риску, не делать её обязательным препятствием каждому водителю;
- проверять CAPTCHA на сервере;
- не записывать телефон в обычные access/error logs;
- при повторном idempotency key с другим payload возвращать конфликт;
- не делать знание чужого idempotency key способом получения PII.

### Stored XSS

В `main.js` напрямую интерполируются в HTML:

- `heroTitle`;
- `service.title`, `description`, `price`, `icon`;
- `review.text`, `name`, `image`.

В `admin.js`:

```js
<a href="tel:${r.phone}">
```

Телефон приходит из публичной заявки без строгой валидации и попадает в атрибут без экранирования. Это создаёт путь **публичная форма → БД → административный DOM**.

Наличие `esc()` для видимого текста не защищает соседний неэкранированный атрибут.

Дополнительная проблема — вставки данных внутрь inline JavaScript:

```html
onclick="openLightbox('...')"
```

HTML-экранирование не является экранированием JavaScript-контекста.

### Исправление

- Использовать `textContent`.
- Создавать DOM-элементы через API или шаблонизатор с автоматическим экранированием.
- Удалить inline `onclick`.
- Телефоны нормализовать до допустимого формата.
- URL проверять по protocol и, где возможно, host allowlist.
- Иконки выбирать из фиксированного списка.
- Не принимать HTML там, где нужен обычный текст.
- Если rich text действительно необходим — использовать проверенный sanitizer.

```js
function makeRequestPhone(phone) {
  if (!/^\+7\d{10}$/.test(phone)) {
    return document.createTextNode('Телефон не указан');
  }

  const link = document.createElement('a');
  link.href = `tel:${phone}`;
  link.textContent = phone;
  link.className = 'request-phone';
  return link;
}

const title = document.createElement('h3');
title.textContent = service.title;
```

### Telegram HTML injection

Поля заявки вставляются в сообщение с `parse_mode: 'HTML'`.

Это не браузерный XSS, но возможны:

- подмена форматирования;
- внедрение ссылок;
- ошибки отправки из-за недопустимой разметки.

Для уведомлений проще использовать plain text без `parse_mode`.

## 1.8. CSP, uploads и логирование

### Content Security Policy

CSP отключена ради Tailwind CDN.

Правильное решение — не сохранять отключённую CSP, а убрать runtime CDN и inline-обработчики.

Пример целевой политики после сборки локальных ресурсов:

```js
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'"],
      imgSrc: ["'self'", 'https://media.example.ru'],
      fontSrc: ["'self'"],
      connectSrc: ["'self'"],
      objectSrc: ["'none'"],
      baseUri: ["'none'"],
      frameAncestors: ["'none'"],
      formAction: ["'self'"],
    },
  },
}));
```

Политику адаптировать к реальным хостам и сначала проверить в Report-Only. Для inline JSON-LD или другой необходимой разметки использовать корректные hashes/nonces, а не глобальный `unsafe-inline`.

На Vercel статические HTML обслуживаются отдельно от Express по `vercel.json`. Значит, **Helmet в API не гарантирует заголовки для `index.html`, `admin.html` и `profile.html`**. Их нужно настроить на уровне хостинга.

### Uploads

Текущий фильтр проверяет расширение незафиксированным regex:

```js
/jpeg|jpg|png|webp|gif/
```

Риски:

- расширение не подтверждает содержимое;
- принимаемый MIME задаёт клиент;
- `memoryStorage()` допускает накопление десятков мегабайт на запрос;
- изображения могут содержать EXIF и координаты;
- фотографии ремонтов обслуживаются как публичные assets либо получают public URL;
- произвольные photo URL/base64 допускаются отдельной веткой.

Рекомендуется:

1. Проверка сигнатуры и декодирование изображения.
2. Ограничение dimensions/pixels и количества файлов.
3. Перекодирование через Sharp.
4. Удаление EXIF.
5. UUID-имена.
6. Отдельные buckets:
   - публичные изображения опубликованных отзывов;
   - приватные фотографии ремонтов.
7. Signed URLs с коротким TTL для приватных фото.
8. Проверка права на конкретный ремонт до выдачи ссылки.
9. Ограничение суммарного request size с учётом лимитов хостинга.

`getPublicUrl()` сам по себе не делает private bucket публичным. Фактическую доступность Supabase-фотографий нужно проверить по конфигурации bucket.

В legacy также стоит проверить удаление файлов: путь берётся из изменяемого `review.image` и проверяется только через `startsWith('/uploads/')`. Нужна проверка, что разрешённый абсолютный путь действительно остаётся внутри upload-каталога.

### Публичные логи

Удалить из production:

- `GET /api/logs`;
- неограниченный `POST /api/debug`;
- vConsole;
- логирование тел запросов авторизации и текстов сообщений боту.

Ограничение массива до 100 элементов не является защитой:

- один элемент может быть большим;
- злоумышленник может вытеснять полезные записи;
- serverless-инстансы имеют разные массивы;
- данные доступны без авторизации.

Нужны structured logs с request ID, redaction и закрытым доступом. Телефоны, пароли, OTP, session tokens, Bot Token и query-параметры авторизации должны маскироваться.

## 1.9. OTP, magic links и VK OAuth

### OTP

Проблемы:

- `Math.random()` вместо криптографического генератора;
- коды хранятся открыто;
- нет надёжного per-challenge бюджета попыток;
- ответ раскрывает существование клиента и его имя;
- код возвращается при `NODE_ENV !== 'production'`;
- отправка Telegram не ожидается через `await`;
- Supabase-последовательность «прочитать → проверить → удалить» не атомарна.

Исправления:

- `crypto.randomInt`;
- HMAC кода с отдельным серверным секретом вместо простого SHA-256 шестизначного пространства;
- TTL и лимит попыток;
- единообразный внешний ответ;
- никакой выдачи OTP из рабочего API;
- атомарное потребление;
- проверка ошибок доставки и записи.

### Magic links

- Создание сессии через GET — изменить на POST.
- Polling GET фактически потребляет сессию и создаёт новую авторизацию — разделить read-only status и POST completion.
- Ответы авторизации: `Cache-Control: no-store`.
- Два конкурентных polling-запроса не должны выдавать две сессии.
- Шестизначные коды могут сталкиваться: нужна соответствующая уникальность и обработка конфликтов.
- `sessionCode` интерполируется в `.or(...)` — валидировать формат и не собирать PostgREST filter из произвольного текста. Это риск инъекции фильтра, не доказанный произвольный SQL injection.
- Polling каждые 2 секунды даёт около 300 запросов за 10 минут на одну вкладку. Нужны backoff, остановка при скрытой вкладке и запрет перекрывающихся запросов.

### VK OAuth

Подтверждено:

- нет `state`;
- токен сессии помещается в query string;
- используются лишние разрешения вроде `offline` в legacy;
- нет достаточных сетевых timeout/error guards;
- legacy автоматически связывает аккаунты по email.

Токен в URL может оказаться в истории, логах и same-origin referrer. `history.replaceState()` уменьшает дальнейшее распространение, но не отменяет уже выполненные запросы.

Рекомендация:

- серверная OAuth-транзакция;
- одноразовый `state`, привязанный к браузеру;
- PKCE там, где поддерживается выбранным актуальным VK flow;
- фиксированный redirect URI;
- минимальный scope;
- выдача cookie сервером;
- redirect на чистый URL;
- никаких автоматических объединений по неподтверждённому email/телефону.

До завершения реализации VK лучше скрыть, а не показывать кнопку с `alert()`.

## 1.10. Защита персональных данных

Система содержит телефоны, Telegram ID, автомобили, фотографии и историю обслуживания.

Необходимо определить:

- оператора и правовое основание обработки;
- политику конфиденциальности;
- состав необходимых данных;
- сроки хранения заявок и фотографий;
- порядок удаления и выгрузки данных;
- права сотрудников;
- резервное копирование и проверку восстановления;
- допустимость передачи данных в Telegram;
- локализацию и трансграничную обработку.

Если сервис работает с персональными данными граждан РФ, применимость требований 152-ФЗ и размещение первичной базы требуют отдельной юридической оценки. Регион Supabase в материалах не указан.

Не пересылать всю заявку в Telegram по умолчанию. Более безопасное уведомление:

> Новая заявка №… · район … · открыть в CRM.

Телефон и детали — после авторизованного перехода. Это снижает распространение PII по устройствам и чатам.

# 2. UI/UX аудит и конверсия — Product & Design

## 2.1. Главная продуктовая задача

Пользователь такого сервиса часто:

- находится на дороге;
- испытывает стресс;
- пользуется телефоном одной рукой;
- имеет плохую связь;
- хочет понять: **«Вы поможете здесь? Когда? Сколько примерно стоит? Как связаться?»**

Поэтому основной продукт — не впечатляющая анимация и не личный кабинет, а **быстрый и достоверный путь к помощи**.

### Что уже хорошо

- Есть sticky mobile CTA.
- Есть `tel:`-ссылки.
- Форма не требует регистрации.
- Предусмотрены услуги, отзывы, этапы работы.
- Есть статус приёма заявок.
- Тёмная палитра и электрический акцент уже подходят тематике.

### Что мешает конверсии

| Наблюдение | Последствие | Рекомендация |
|---|---|---|
| H1 и подзаголовок изначально пустые | Пользователь зависит от API и JS | Выдать готовый HTML |
| Телефон до загрузки API — демонстрационный | Возможен звонок не туда | Реальный номер в статической разметке |
| Hero на весь экран | Основная информация может уходить ниже сгиба | Компактный mobile hero |
| Много равнозначных акцентов | Неясно главное действие | Звонок — primary, заявка — secondary |
| Регион описан слишком обобщённо | Неясна возможность выезда | Город, районы, трассы, условия километража |
| «30–60 минут» без контекста | Риск ложного ожидания | Показывать только подтверждённые условия |
| Калькулятора нет | Запрошенная функция пока не реализована | Добавить лёгкую оценку диапазона |
| Маскот запускает onboarding сам | Отвлекает от срочного действия | Помощник только по запросу |
| Данные об услугах и отзывах зависят от JS | Пустые секции при сбое | Статический/SSR-контент |

1. **Hero**

   - специализация и оборудование;
   - гарантия с условиями;
   - подтверждаемые отзывы.

4. **Услуги и цены**
   - работа;
   - диагностика;
   - выезд;
   - дополнительные условия.

5. **Калькулятор предварительной оценки**

6. **Как проходит вызов**
   - уточнение;
   - согласование;
   - диагностика;
   - ремонт и документы.

7. **Кейсы и отзывы**

8. **FAQ**
   - выезд за город;

   - что делать, если ремонт на месте невозможен;

Личный кабинет — вторичный сценарий для повторных клиентов. Не заставлять впервые приехавшего посетителя сначала разбираться в программе лояльности.

## 2.3. Hero-секция

Пример направления текста, требующий заполнения реальными данными:

> **Автоэлектрик с выездом в [городе и районе]**  
> Не заводится автомобиль, разряжается АКБ или появилась ошибка? Уточним симптомы, согласуем выезд и стоимость диагностики.

Кнопки:

- **Позвонить мастеру**
- **Перезвоните мне**

Под ними:

- «Выезд от … ₽»;
- «Диагностика от … ₽»;
- «Стоимость ремонта согласуем до начала работ».

Не использовать неподтверждённые «24/7», «приедем за 30 минут» и «ремонт любых авто».

## 2.4. Статус мастера

`acceptingRequests: boolean` — слишком грубая модель.

Рекомендуемая структура:

```ts
type Availability = {
  state: 'available' | 'busy' | 'offline' | 'unknown';
  updatedAt: string;
  validUntil: string;
  estimatedWindow?: {
    from: string;
    to: string;
  };
};
```

Отображение:

| Состояние | Текст | Действие |
|---|---|---|
| `available` | «Готов принять вызов» | Позвонить |
| `busy` | «На вызове. Уточните ближайшее время» | Позвонить / оставить заявку |
| `offline` | «Сейчас не на связи» | Заявка с честным сроком ответа |
| `unknown` или устаревший статус | «Уточните доступность по телефону» | Позвонить |

Сейчас отсутствие настроек интерпретируется как `acceptingRequests !== false`, то есть фактически как доступность. При сбое API это вводит пользователя в заблуждение.

Статус должен быть текстовым, а не только цветным. Не показывать точные координаты мастера публично.

## 2.5. Калькулятор и прайс

В предоставленном проекте калькулятора нет.

### MVP-калькулятор

Достаточно трёх вопросов:

1. Где автомобиль?
2. Что происходит?
3. Нужен выезд сейчас или по записи?

Результат — **диапазон**, а не выдуманная точная цена:

> Предварительно: …–… ₽.  
> Включено: выезд в выбранной зоне и диагностика.  
> Запчасти и дополнительные работы согласуются отдельно.

Технически:

- правила доступны локально;
- нет обязательного API-запроса на каждый шаг;
- цена хранится числом в минимальных денежных единицах;
- версия прайса сохраняется с заявкой;
- сервер не доверяет переданной клиентом итоговой цене.

Для прайса заменить строку `"от 1 500 ₽"` структурой:

```ts
type ServicePrice = {
  currency: 'RUB';
  minMinor: number;
  maxMinor: number | null;
  pricingMode: 'fixed' | 'from' | 'range' | 'after_diagnosis';
};
```

Услуга «от …» должна объяснять, что входит в минимум.

## 2.6. Визуальный стиль: современный, но не перегруженный

Текущий сайт уже использует dark UI, крупную типографику, скруглённые карточки, glow и GSAP. Поэтому проблема не буквально в «отсутствии современного стека», а в шаблонности и недостатке реального содержания.

### Рекомендуемое направление

**Sleek Dark Bento с ограниченными электрическими акцентами.**

- Графитовый фон вместо сплошного чёрного.
- 2–3 уровня поверхности.
- Один основной cyan-акцент.
- Янтарный — только для предупреждений.
- Чёткая типографическая иерархия.
- Настоящие фотографии мастера и работ.
- Минимум декоративного blur.
- Bento — для доверия и кейсов, а не для разрушения порядка чтения.

Нео-брутализм применять дозированно: жёсткая рамка, крупная цифра, контрастный CTA. Одновременно смешивать glassmorphism, неон, брутализм и множество парящих элементов не стоит.

```css
:root {
  color-scheme: dark;
  --bg: #0d1117;
  --surface: #151b23;
  --surface-raised: #1c2530;
  --text: #f3f6fa;
  --muted: #a8b3c2;
  --accent: #4dd7ff;
  --warning: #ffc46b;
  --border: #344253;
  --radius-card: 1.25rem;
}
```

Цвета — стартовые tokens, не сертификат WCAG. Все фактические пары проверить на контраст.

## 2.7. Маскот как полезный помощник

Маскот уже не полностью статичен: есть onboarding, контекстные подсказки и реакция на заявку. Но это преимущественно **экскурсия по сайту**, а не помощь с проблемой.

### Что изменить

- Не открывать автоматически через 1,2 секунды.
- Не прокручивать страницу без явного желания пользователя.
- Добавить «Не показывать».
- Не перекрывать sticky CTA.
- Основной сценарий: «Помочь описать неисправность».

### Сценарий

```text
Что случилось?
├── Не заводится
│   ├── Стартер не крутит
│   ├── Крутит, но двигатель не запускается
│   └── Не уверен
├── Разряжается аккумулятор
├── Ошибка на панели
└── Другая проблема
```

Результат:

- краткое описание для мастера;
- кнопка «Передать в заявку»;
- кнопка «Позвонить»;
- честное пояснение: «Это предварительное уточнение, не диагностика».

На первом этапе достаточно детерминированного JSON-сценария. LLM не нужен: он увеличит стоимость, задержки и риск ошибочных рекомендаций.

При дыме, запахе горящей проводки и иной опасности помощник должен прекращать диагностический опрос и показывать краткую рекомендацию перейти в безопасное место и обратиться к экстренным службам при необходимости. Никаких инструкций замыкать контакты или обходить защиту.

## 2.8. Accessibility и качество формы

Нужно исправить:

- связать `label` с input через `for`/`id`;
- добавить `autocomplete="tel"`, `inputmode="tel"`;
- именовать icon-only кнопки;
- добавить `aria-expanded` мобильному меню;
- использовать `<dialog>` либо корректную dialog-семантику;
- управление фокусом, Escape, возврат фокуса;
- видимый `:focus-visible`;
- `aria-live` для результата формы;
- достаточные размеры зон нажатия;
- отступ под `env(safe-area-inset-bottom)`;
- работу при увеличении текста;
- отключение autoplay отзывов либо понятную паузу.

Форму отделить от `mascot.js`: отказ декоративного помощника не должен отключать отправку заявки.

После отправки:

- не закрывать подтверждение слишком быстро;
- показывать номер заявки;
- сохранять понятный путь к звонку;
- различать «заявка сохранена» и «мастер уведомлён».

## 2.9. Продуктовые метрики

Измерять:

- `call_click`;
- `request_open`;
- `request_submit_success`;
- `request_submit_error`;
- `calculator_complete`;
- `qualified_lead`;
- `lead_contacted`;
- `repair_booked`;
- время до первого ответа.

`call_click` — не состоявшийся звонок и не продажа.

Главная метрика — стоимость и доля квалифицированных обращений, а не вовлечённость в маскота.

Отдельно: отсутствие визита к автоэлектрику 6 месяцев не обязательно означает churn. Для разовых аварийных услуг текущая retention-модель может провоцировать ненужные сообщения. Повторный контакт привязывать к реальному обслуживанию и предпочтениям клиента.

# 3. Производительность и оптимизация — Core Web Vitals

## 3.1. Главные источники задержек

1. Пустой H1 заполняется после `/api/data`.
2. `/api/data` делает четыре Supabase-запроса.
3. Возможен cold start serverless-функции.
4. Tailwind компилируется в браузере.
5. Несколько блокирующих CDN-скриптов.
6. vConsole загружается на публичных страницах.
7. Lucide подключён целиком с `@latest`.
8. Swiper bundle используется ради нескольких отзывов.
9. Google Fonts подключены и через `<link>`, и через CSS `@import`.
10. Загружаются две гарнитуры с множеством начертаний.
11. Hero использует удалённое изображение шириной 1920 px без responsive sources.
12. Несколько GSAP-анимаций накладываются на одни и те же `.reveal`-карточки.
13. Hero-контент дополнительно скрывается/появляется по timeline.

Последний пункт может ухудшать фактическое время видимости главного контента даже при быстрой сети.

## 3.2. Реалистичность LCP < 1 секунды

**LCP < 1 секунды — разумная stretch-цель для хорошего 4G и CDN cache hit, но не честная гарантия для медленного 3G.**

При высокой задержке сети и холодном кеше одна доставка HTML уже занимает существенную долю секунды.

Разделить критерии:

| Метрика | Цель |
|---|---|
| LCP, лаборатория, согласованный профиль хорошего 4G | Стремиться к < 1,0 с |
| LCP, реальные mobile-сессии p75 | ≤ 2,5 с |
| INP, реальные сессии p75 | ≤ 200 мс |
| CLS, штатные лабораторные сценарии | 0 |
| CLS, полевые данные p75 | Внутренний бюджет ≤ 0,02; стандарт good ≤ 0,1 |
| Медленный 3G | Главное содержание и звонок не зависят от JS/API |

Нельзя оптимизировать только Lighthouse score и игнорировать фактическую доступность CTA.

## 3.3. Бюджет ресурсов

Предлагаемый бюджет для первого экрана, после сжатия при передаче:

| Ресурс | Бюджет |
|---|---:|
| HTML | 15–25 КБ |
| CSS | 10–20 КБ |
| Начальный JS | 0–25 КБ |
| Шрифт | 0–45 КБ |
| Изображения первого экрана | 0–80 КБ |
| Суммарно | Ориентир до 150–200 КБ |
| Критические сторонние запросы | 0 |

Это бюджеты для проверки сборкой, а не оценка текущего веса.

На экстремально медленной связи даже 200 КБ — немало. Поэтому критический hero можно сделать преимущественно текстовым.

## 3.4. Статический first paint

В HTML сразу должны находиться:

- H1;
- описание;
- реальный номер;
- зона выезда;
- базовые цены;
- услуги;
- отзывы.

Динамически обновлять только статус мастера и действительно изменяемые детали.

Рекомендуемая схема:

```text
CDN → готовый HTML + CSS
       ├── звонок работает сразу
       ├── услуги видны сразу
       └── маленький JS обновляет статус и форму
```

Для no-JS формы возможен обычный POST с HTML-страницей подтверждения. Защиты и валидация должны быть теми же, что у JSON-варианта.

## 3.5. Шрифты

- Выбрать одну гарнитуру.
- Либо использовать системный стек — самый лёгкий вариант.
- Удалить повторный Inter из `@import`.
- При self-hosting включить кириллицу и необходимые символы.
- Сравнить вес variable font с двумя статическими начертаниями.
- Preload только действительно используемого критического WOFF2.
- `font-display: swap` или `optional` — по результатам UX-тестов.
- Подстроить fallback metrics, чтобы смена шрифта не меняла геометрию.

`@theme` в обычном CSS не создаёт Tailwind v4 utilities без build pipeline. Текущий комментарий «Tailwind v4» не соответствует фактической схеме с браузерным CDN.

## 3.6. Изображения и SVG

### Hero и фотографии

Если фотография нужна на первом экране:

```html
<picture>
  <source
    type="image/avif"
    srcset="/images/master-480.avif 480w,
            /images/master-960.avif 960w"
    sizes="(max-width: 767px) 100vw, 40vw"
  />
  <source
    type="image/webp"
    srcset="/images/master-480.webp 480w,
            /images/master-960.webp 960w"
    sizes="(max-width: 767px) 100vw, 40vw"
  />
  <img
    src="/images/master-960.jpg"
    width="960"
    height="720"
    alt="Мастер выполняет диагностику автомобиля"
    fetchpriority="high"
    decoding="async"
  />
</picture>
```

- LCP-изображение не делать lazy.
- Остальные фото — `loading="lazy"`.
- AVIF сравнить с WebP по качеству, весу и декодированию.
- Декоративный фон, почти скрытый overlay, лучше удалить.
- Unsplash-фотографии автомобилей не заменяют доказательства реальной работы.

### SVG

`mascot.svg` не предоставлен, поэтому его фактическую сложность оценить нельзя.

Проверить:

- не встроен ли внутрь огромный base64 PNG;
- количество paths;
- filters и blur;
- metadata;
- внешние ссылки;
- сохранность `viewBox`.

Оптимизировать через SVGO и визуальную регрессию. Иконки импортировать выборочно либо подготовить локальные SVG.

## 3.7. CLS, rendering и кеширование

Для нулевого CLS в штатных сценариях:

- не вставлять H1 после API;
- задавать размеры изображениям;
- резервировать блок статуса;
- не добавлять баннеры перед уже видимым контентом;
- не менять высоту шапки на scroll;
- избегать поздней генерации CSS;
- проверять загрузку шрифта;
- не анимировать размеры layout-элементов.

Кеширование:

| Ответ | Политика |
|---|---|
| Fingerprinted JS/CSS/images | Долгий cache + `immutable` |
| Публичный HTML | CDN cache с управляемой инвалидацией |
| Публичные услуги | Кеширование с учётом обновления прайса |
| Статус мастера | Короткий TTL и контроль устаревания |
| Auth, OTP, профиль, CRM | `private, no-store` |

Не кешировать персональные API на CDN или в service worker.

## 3.8. Проверка результата

Проверять на staging:

- холодный и тёплый cache;
- средний Android;
- iOS Safari;
- медленный 3G и 4G с зафиксированными параметрами;
- недоступный Supabase;
- заблокированные сторонние домены;
- JS disabled;
- reduced motion;
- увеличение текста и клавиатуру.

Инструменты:

- Lighthouse CI;
- WebPageTest;
- Chrome Performance;
- `web-vitals` для RUM;
- Playwright для сценариев отказа и layout-regression.

При небольшом трафике данных CrUX может не хватать. Нужны собственные аккуратно собранные метрики без PII.

# 4. Живые современные анимации — Living Motion & Interactions

## 4.1. Базовый принцип

**Анимация подтверждает действие, а не задерживает помощь.**

На первом экране:

- H1 виден немедленно;
- номер доступен немедленно;
- CTA не ждёт окончания timeline;
- отсутствие motion-библиотеки ничего не ломает.

## 4.2. Выбор технологий

| Технология | Когда использовать | Решение для проекта |
|---|---|---|
| CSS transitions/keyframes | Нажатия, состояния, лёгкие акценты | Основной вариант |
| Web Animations API | Простые управляемые последовательности | Хорошо подходит Vanilla/Astro |
| GSAP | Сложная синхронизация SVG и сцен | Точечно, lazy-load |
| Motion for React / Framer Motion | React-компоненты со сложными переходами | Только в React-островах или CRM |
| Lenis | Особая desktop-режиссура прокрутки | Не рекомендуется по умолчанию |
| Rive/Lottie | Сложный маскот | Только при доказанной пользе и бюджете |
| Canvas/WebGL particles | Декоративные эффекты | Не нужны для MVP |

Не устанавливать GSAP, Motion, Lenis и Lottie одновременно ради ощущения «современности».

Для этого сайта нативная прокрутка предпочтительнее smooth-scroll hijacking: она предсказуема на мобильных, с клавиатурой и assistive technologies.

## 4.3. Motion-система

| Элемент | Эффект | Длительность |
|---|---|---:|
| CTA | Небольшое сжатие при нажатии | 100–160 мс |
| Карточка услуги | Смещение вверх на 2–3 px | 160–220 мс |
| Открытие помощника | Opacity + translateY | 180–240 мс |
| Успех формы | Галочка/короткое подтверждение | 200–300 мс |
| SVG-провод | Однократный пробег сигнала | 400–700 мс |
| Маскот | Небольшая реакция на выбор | До 300 мс |

Не анимировать `width`, `height`, `top`, `left` в интерактивных циклах. Предпочитать `transform` и `opacity`.

## 4.4. Пример микроанимации CTA

```css
.emergency-cta {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  min-block-size: 3rem;
  transition:
    transform 140ms ease,
    background-color 140ms ease;
}

.emergency-cta:focus-visible {
  outline: 3px solid white;
  outline-offset: 4px;
}

@media (hover: hover) and (pointer: fine) {
  .emergency-cta:hover {
    transform: translateY(-2px);
  }
}

.emergency-cta:active {
  transform: scale(.98);
}

@media (prefers-reduced-motion: reduce) {
  html {
    scroll-behavior: auto;
  }

  .emergency-cta,
  .service-card,
  .mascot-panel {
    transition: none;
    animation: none;
    transform: none;
  }
}
```

Для JS-анимаций также проверять media query. Одного CSS недостаточно, если GSAP продолжает управлять элементом.

## 4.5. Провода, искры и маскот

### Провода

- Один SVG-path в декоративной части карточки.
- Изменение `stroke-dashoffset` при hover/focus.
- Без постоянного mouse tracking на телефоне.
- Если tracking нужен на desktop — обновление через `requestAnimationFrame`.
- Декорации: `aria-hidden="true"` и `pointer-events: none`.

### Искры

- Только краткий локальный акцент.
- Не использовать вспышки и стробирование.
- Не создавать непрерывный canvas-loop для всей страницы.
- Не ставить эффект поверх текста.

### Маскот

Если SVG состоит из отдельных групп, можно анимировать взгляд и руку. Если SVG — обёртка над растровой картинкой, предварительно потребуется подготовка исходника.

Рекомендуемые состояния:

```text
idle → listening → suggesting → submitted
                    └────────→ error
```

- `idle` преимущественно неподвижен;
- `listening` реагирует на выбор;
- `submitted` подтверждает только успешное сохранение;
- `error` не делает вид, что заявка отправлена.

Анимации приостанавливать вне viewport и на скрытой вкладке. Reduced motion и Save-Data рассматривать как сигналы уменьшить необязательные эффекты.

# 5. Модернизация технологического стека

## 5.1. Нужна ли миграция?

**Для устранения P0 миграция не нужна.** Безопасность исправляется в текущем Express.

После стабилизации оптимальный баланс:

> **Astro для публичного сайта + единый Express/TypeScript API + Supabase/Postgres + надёжный worker уведомлений.**

React добавлять только там, где сложность интерфейса действительно оправдывает его.

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| Vanilla + Vite | Минимальная миграция, небольшой runtime | Больше ручной дисциплины UI | Хороший быстрый этап |
| Astro | Статический HTML, islands, мало JS | Не заменяет архитектуру CRM | Предпочтительно для лендинга |
| Next.js | SSR, React, единый full-stack подход | Выше сложность кеша и эксплуатации | При развитии большого кабинета |
| Vite + React | Удобен для CRM | SPA не лучший default для SEO-лендинга | Использовать для админки при росте |
| Tailwind CSS v4 | Design tokens, сборка utilities | Не исправляет UX автоматически | Опционально, только build-time |

Tailwind v4 выбирать с учётом поддерживаемых браузеров. Для аудитории на старых телефонах нужна явная browser support policy.

## 5.2. Сначала устранить расхождение реализаций

Сейчас `npm start` запускает не ту систему, которая развёртывается на Vercel.

Необходимо:

1. Один модуль `createApp()`.
2. Один набор routes/services/repositories.
3. Отдельные тонкие entrypoints для локального Node и serverless.
4. Единая схема API.
5. Один способ авторизации.
6. Один источник бизнес-правил.
7. Удаление legacy после проверки миграции.

### Подтверждённые функциональные дефекты

| Дефект | Следствие |
|---|---|
| HTML содержит `login-form`/`login-pwd`, JS ищет `auth-btn`/`auth-username`/`auth-password` | Форма входа не связана с новым обработчиком |
| Загрузки фото и часть delete-запросов используют `x-admin-password`, Supabase API ждёт Bearer | Эти действия получают 401 |
| `loadAndShow()` не вызывает `loadRequests()` и `loadClients()` | CRM может показывать пустые списки |
| `/api/data` больше не содержит CRM, но frontend продолжает ожидать её там | Несовместимый контракт |
| `/api/analytics` возвращает `{ stats: ... }`, UI читает старые верхнеуровневые поля | KPI показывают нули/неверные значения |
| В `renderGreeting()` используется необъявленная `level` | Падение рендера профиля |
| Logout обращается к отсутствующим `stepPhone`, `stepOtp` и другим переменным | Ошибка сценария выхода |
| В `api/index.js` нет вызываемых frontend routes автомобилей | Добавление/удаление авто не работает |
| `/api/reviews/:id` объявлен до `/api/reviews/reorder` для PUT | `reorder` перехватывается как `id` |
| `openRepairModal()` задаёт hidden client ID до `form.reset()` | ID может сбрасываться |
| В Supabase repair route теряются `reminderDate`/`reminderText` | Напоминание из формы не сохраняется |
| `createdAt` и `created_at`, camelCase и snake_case смешаны | Неверные даты и поля |
| Supabase magic возвращает `code`, legacy — нет, а frontend требует его | Вход через legacy ломается |
| Frontend имеет вызов Telegram Widget endpoint, но маршрута нет | Сценарий не завершён |
| Supabase `cachedToken` не обновляется после изменения settings | Новый Bot Token может не примениться |
| Ошибки Supabase часто игнорируются | API сообщает об успехе без сохранения |

Отдельно:

- `scripts/migrate_to_supabase.js` создаёт мастера без `username`, ожидаемого новым входом.
- Есть две разные миграции с разным поведением.
- Regex-скрипты рефакторинга не должны быть частью штатного процесса изменения production-кода.
- В backend не показана загрузка `.env`, хотя её выполняют миграционные скрипты. Локальная конфигурация должна быть явной.
- Нет lockfile в предоставленных материалах: нельзя подтвердить воспроизводимость зависимостей.

## 5.4. Надёжная доставка уведомлений

Текущая схема «insert → sendMessage → игнорировать ошибки» не гарантирует ни сохранение, ни доставку.

Нужно:

1. В транзакции создать заявку.
2. В той же транзакции создать outbox event.
3. Только после commit ответить пользователю.
4. Worker забирает задачи с блокировкой/lease.
5. Отправляет уведомление.
6. Записывает попытку, успех или ошибку.
7. Повторяет с backoff.
8. После лимита попыток — dead-letter и alert.

Два отдельных `.insert()` через Supabase SDK не образуют транзакцию автоматически. Использовать узкую SQL-функцию/RPC или серверное DB-соединение с транзакцией.

Пример полей outbox:

```text
id
event_type
aggregate_id
payload
created_at
attempts
next_attempt_at
locked_until
delivered_at
last_error_code
```

Telegram `sendMessage` не даёт универсальной гарантии exactly-once. Если worker упал после отправки, но до записи результата, возможен дубль. Поэтому:

- стремиться к at-least-once;
- включать ID заявки;
- не терять сообщение ради попытки добиться недостижимого exactly-once.

На Vercel не полагаться на fire-and-forget promise и `setTimeout` после ответа. Использовать поддерживаемую очередь/worker-модель.

## 5.5. Модель данных

Вынести из JSON-массивов:

- `cars`;
- `repairs`;
- `repair_photos`;
- `reminders`.

Текущая Supabase-схема «прочитать repairs → добавить элемент → перезаписать массив» допускает lost update при конкурентных изменениях.

Предлагаемые таблицы:

```text
clients
client_identities
masters
master_roles
sessions
auth_challenges
requests
request_events
cars
repairs
repair_photos
reminders
services
reviews
public_settings
availability
webhook_inbox
notification_outbox
audit_events
```

Основные ограничения:

- foreign keys;
- уникальная пара `(provider, provider_subject)`;
- TTL и индексы сессий;
- enum/check для статусов;
- неотрицательная стоимость;
- `timestamptz` для событий;
- `date` для календарных дат;
- индексы по `client_id`, `status`, `created_at`;
- уникальный idempotency key в правильном scope.

Не делать телефон безусловным доказательством личности. Отдельно хранить подтверждение номера и политику общих семейных/корпоративных телефонов.

Напоминание не должно считаться ремонтом: сейчас synthetic repair увеличивает количество визитов и может влиять на скидку.

Аналитику считать SQL-агрегациями с определённой временной зоной. Сравнение даты `YYYY-MM-DD` с полным ISO timestamp строкой даёт ошибки на границе периода.

| Область | Проверка | Ожидаемый результат |
|---|---|---|
| Public API | Запрос без сессии | Только публичный DTO |
| Admin API | Нет/истекла/отозвана сессия | 401 |
| RBAC | Мастер пытается создать владельца | 403 |
| Ownership | Клиент A запрашивает данные B | Отказ без утечки |
| Webhook | Нет/неверный secret | 403 |

| Magic link | Два конкурентных completion | Одна сессия |
| OTP | Исчерпан бюджет попыток | Challenge блокируется |

## Итоговое решение

Проект имеет полезный MVP-каркас, но сейчас страдает прежде всего от **опасной авторизации, раскрытых секретов и незавершённого перехода между двумя backend-реализациями**.

Правильный порядок модернизации:

1. **Отозвать секреты и закрыть пути захвата.**
2. **Объединить backend и восстановить основные сценарии.**
3. **Обеспечить целостность заявок, сессий и уведомлений.**
4. **Сделать лендинг статическим, лёгким и достоверным.**
5. **Провести mobile-first редизайн.**
6. **Добавить деликатную анимацию и полезного маскота.**

**Рекомендуемый целевой продукт:** быстрый Astro-лендинг с доступным без JavaScript звонком, безопасный модульный Express API, закрытая CRM на Supabase/Postgres и надёжная доставка Telegram-уведомлений. Современность здесь должна выражаться прежде всего в скорости, ясности и надёжности — не в количестве эффектов.
