## 🎯 ИДЕЯ №1: Единый профиль клиента с мультиавторизацией (Account Linking)

### 1. Проблема
При текущей реализации вход через разные провайдеры (Telegram Magic Link / Widget и VK ID One Tap / OAuth) создаёт в базе данных Supabase разные строки в таблице `clients`:
* **Профиль Telegram:** `id: 5ca44a9e-026b-4b1f-b5db-54f378a9f149`, `@Tri_chasa_nazad` (`telegram_id: 6208918931`)
* **Профиль VK ID:** `id: 19e4e551-4454-4710-8a6d-a4effc211201`, `Sid Vicious` (`vk_id: 1125744855`)

Клиент не должен иметь два разных кабинета: история автомобилей, ремонтов и заявок должна быть единой вне зависимости от того, через что он вошёл.

### 2. Целевая архитектура решения

```
                   ┌────────────────────────────────────────────────┐
                   │            ЕДИНЫЙ ПРОФИЛЬ КЛИЕНТА              │
                   │               (таблица clients)                │
                   │                                                │
                   │  id: UUID                                      │
                   │  name: "Sid Vicious / Три часа назад"          │
                   │  phone: "+7 (999) 000-00-00"                   │
                   │  vk_id: "1125744855"                           │
                   │  telegram_id: "6208918931"                     │
                   │  cars: [...]                                   │
                   │  repairs: [...]                                │
                   └───────▲───────────────▲───────────────▲────────┘
                           │               │               │
            ┌──────────────┴──────┐ ┌──────┴──────┐ ┌──────┴────────┐
            │   Вход через VK     │ │  Telegram   │ │   Телефон     │
            │      One Tap        │ │ Magic Link  │ │   (СМС/OTP)   │
            └─────────────────────┘ └─────────────┘ └───────────────┘
```

### 3. Механизм связывания (Account Linking & Merge)

#### А. Привязка из Личного Кабинета (`profile.html`):
1. В личном кабинете пользователя выводится блок **«Связанные аккаунты»**:
   - `VK ID`: Статус (Подключен / Не привязан) + кнопка «Привязать / Отвязать».
   - `Telegram`: Статус (Подключен / Не привязан) + кнопка «Привязать Telegram».
   - `Телефон`: Поле с подтверждением номера.
2. При нажатии «Привязать Telegram»:
   - Генерируется защищенный одноразовый токен привязки: `POST /api/client/link/telegram` -> `token`.
   - Формируется диплинк бота: `https://t.me/Autoelectrical_Official_bot?start=link_<token>`.
   - Пользователь переходит в бота, жмёт `Start`.
   - Бот считывает `token`, связывает `telegram_id` и `telegram_username` с текущим `client_id` и присылает подтверждение.

#### Б. Автоматическое слияние профилей (Merge Strategy):
Если привязываемый Telegram (или VK) уже был привязан к старому профилю (дубликату):
1. Происходит перенос всех связанных данных:
   - Массивы `cars` объединяются (исключая точные дубликаты по VIN/госномеру).
   - Массивы `repairs` объединяются и сортируются по дате.
   - Заявки в таблице `requests` перепривязываются на основной `client_id`.
2. Пустой дублирующий профиль архивируется или удаляется.
3. Вся история ремонтов и авто сохраняется без потерь.

#### В. Единый якорь по номеру телефона:
- Телефон — универсальный идентификатор автовладельца.
- Если номер телефона совпадает при авторизации через любой провайдер, бэкенд автоматически дописывает недостающий `vk_id` или `telegram_id` к существующей карточке клиента.

### 4. Необходимые эндпоинты (Roadmap задачи):
1. `GET/POST /api/client/link/telegram/start` — генерация токена для бота.
2. Обработчик бота на команду `/start link_:token` — подтверждение привязки.
3. `GET/POST /api/client/link/vk/start` — привязка VK ID к уже активной сессии.
4. UI компоненты в `profile.html` и `profile.js`: статус-карточки привязанных сервисов.

## ⚡ ИДЕЯ №2: Комплексное ускорение сайта (Target: ~250–350 ms)

### 1. Результаты живой телеметрии (Замер от 18.09.2026)
Встроенный счётчик производительности (`perf-widget.js`) зафиксировал среднее время загрузки **1592 ms** (1.6 с) со следующей раскладкой:

| Метрика / Ресурс | Время | Статус | Причина задержки |
|---|---|---|---|
| **Сервер (TTFB)** | **40 ms** | 🟢 Отлично | Vercel Edge CDN отдаёт базовый HTML молниеносно |
| **`images.unsplash.com`** | **1 238 ms** | 🔴 Критично | Внешнее фоновое изображение в Hero (1920px), блокирует сеть |
| **`/api/data`** | **791 ms** | 🔴 Критично | 4 параллельных запроса к Supabase без HTTP-кеширования |
| **DOM Ready** | **903 ms** | 🟡 Задержка | Парсер блокируется runtime-скриптом `cdn.tailwindcss.com` (400 КБ) |
| **Скрипты `main.js`, `swiper`, `mascot`** | **~350 ms** | 🟡 Задержка | Последовательная загрузка без локализации |

### 2. План оптимизации (Пошаговый Roadmap):

#### Шаг 1. Локализация и сжатие фонового изображения Hero (Минус ~1.2 сек)
- Скачать фото с Unsplash локально в папку `public/img/hero-bg.webp`.
- Сжать в современный формат WebP с качеством 80% и уменьшенным разрешением.
- Вес снизится с нескольких мегабайт до ~40–50 КБ.
- Время отдачи с Vercel Edge составит **20–30 ms** вместо **1238 ms**.

#### Шаг 2. Edge-кеширование эндпоинта `/api/data` (Минус ~750 ms)
- В `api/index.js` для маршрута `GET /api/data` добавить заголовок:
  ```javascript
  res.setHeader('Cache-Control', 's-maxage=60, stale-while-revalidate=300');
  ```
- Публичные данные лендинга (услуги, контакты, отзывы) будут мгновенно отдаваться из памяти Edge CDN за **15–25 ms** вместо 791 ms ожидания базы Supabase.

#### Шаг 3. Замена runtime-компилятора Tailwind на статический CSS (Минус ~400 ms)
- Текущий `cdn.tailwindcss.com` весит ~400 КБ и запускает компилятор прямо в браузере клиента.
- Заменить на предкомпилированный компактный CSS-файл (~25 КБ).
- Разгрузит процессор мобильных устройств и сократит DOM Ready с 900 ms до 150 ms.

#### Шаг 4. Локализация внешних шрифтов Google Fonts
- Шрифты `Montserrat` и `Inter` скачать в папку `public/fonts/` в формате `.woff2`.
- Устранит внешние DNS/TLS задержки к серверам Google в РФ (экономия до 1.5 сек на «холодных» визитах).

#### Шаг 5. Вендорные библиотеки в локальном хранилище (`/js/vendor`)
- Локализовать `swiper-bundle.min.js`, `lucide.min.js`, `gsap.min.js`.
- Использовать атрибуты `defer` для устранения блокировок рендеринга.

## 🚀 ВНЕДРЁННЫЙ МЕХАНИЗМ: Сквозная омниканальная идентификация клиентов («Инкогнито» ➔ «Профиль» v1.3.0)

> **Статус:** Внедрено в продакшн (Релиз v1.3.0, коммит `a6d3806`)  
> **Бизнес-цель:** Гарантировать 100% сохранность и непрерывность истории ремонтов, гаража и гарантийных обязательств, независимо от того, обратился ли клиент «инкогнито» с лендинга, через звонок мастеру или через соцсети.

### 1. Архитектурная концепция
Единым универсальным бизнес-ключом (Primary Key реального мира) является **нормализованный номер телефона** в формате E.164 (`+7XXXXXXXXXX`). 

Система связывает три разрозненных источника:
1. **Публичная заявка на сайте** (`POST /api/requests` ➔ телефон, имя, проблема);
2. **Карточка ремонта мастера в CRM** (`POST /api/clients/:id/repairs` ➔ создаётся профиль по телефону);
3. **Личный кабинет клиента** (`/profile.html` ➔ гараж, история ТО, напоминания, гарантия).

```
                      [ Лендинг (Заявка с сайта) ]
                                   │ (phone)
                                   ▼
[ Мастер в CRM: Ремонт ] ──► [ Таблица clients ] ◄── [ Вход по ПИН / Magic Link ]
 (запись по телефону)              ▲ (phone)
                                   │
                      [ Telegram-бот / VK ID ]
                      (One-Tap Share Contact / Merge)
```

### 2. Спецификация 5 уровней механизма

#### Уровень 1. Smart-Merge на бэкенде (`mergeClientAccounts`)
* **Файл:** `api/index.js`
* **Логика работы:**
  * При подтверждении номера телефона клиентом (в профиле, боте или форме) система ищет в таблице `clients` существующие профили с этим телефоном.
  * Если обнаружен дубликат (например, профиль, созданный мастером для ремонта, и пустой профиль авторизации Telegram), запускается слияние `mergeClientAccounts(targetId, sourceId)`:
    * Объединяются массивы `repairs` (с дедупликацией по `id`);
    * Объединяются автомобили `cars` (с дедупликацией по марке/госномеру);
    * Идентификаторы соцсетей (`telegram_id`, `telegram_chat_id`, `vk_id`, `telegram_username`) переносятся в целевой профиль;
    * Все активные токены сессий из `auth_sessions` переназначаются на целевой профиль;
    * Временный пустой профиль удаляется.
  * В эндпоинте `POST /api/client/profile/phone` при сохранении недостающего телефона срабатывает авто-слияние и выдача обновленной сессии.

#### Уровень 2. Telegram Bot: One-Tap подтверждение контакта (`request_contact`)
* **Файл:** `api/index.js` (вебхук `/api/telegram-webhook` и polling `bot.on('contact')`)
* **Логика работы:**
  * При команде `/start auth_<session>` для клиента без сохранённого телефона бот отправляет нативную кнопку Telegram:
    `[ 📱 Поделиться номером для поиска авто ]` (`request_contact: true`).
  * При тапе Telegram передаёт официальный контакт `msg.contact.phone_number`.
  * Бэкенд нормализует телефон, запускает Smart-Merge с профилем мастера, убирает клавиатуру (`remove_keyboard: true`) и одобряет сессию входа. Браузер клиента мгновенно открывает профиль с готовыми ремонтами.

#### Уровень 3. Прямой доступ (Magic Link) для клиента из CRM
* **Эндпоинт:** `GET /api/clients/:id/magic-link` (защищён `authCheck`).
* **Интерфейс мастера:** В `admin.html` и `admin.js` в карточке клиента добавлены кнопки:
  * `📋 Скопировать ссылку` (`https://чекгорит.рф/profile.html?auth=TOKEN`);
  * `💬 В WhatsApp` — открывает чат с предзаполненным сообщением и ссылкой;
  * `✈️ В Telegram` — отправляет ссылку через нативный шеринг.
* **Клиентский UX:** В `profile.js` при открытии ссылки с `?auth=TOKEN` токен сохраняется в `localStorage`, параметр удаляется из URL (`replaceState`), и клиент мгновенно попадает в свой профиль без логинов и паролей.

#### Уровень 4. Мгновенная гостевая сессия при отправке заявки на лендинге
* **Эндпоинт:** `POST /api/requests`
* **Логика работы:**
  * При создании заявки проверяется наличие клиента по телефону. Если его нет — создаётся профиль `{ id, name, phone, cars: [], repairs: [] }`.
  * Создаётся сессионный токен `createSession(client.id)` и возвращается в ответе.
  * В `main.js` токен сохраняется в `localStorage.setItem('ae_client_token', json.token)`.
  * В модальном окне успеха заявки скрываются поля формы и появляется карточка:
    *«Заявка успешно принята! Для вашего номера создана сервисная книжка»* + кнопка `[ 🚗 Открыть личный кабинет ]`.

#### Уровень 5. Вход по номеру телефона и 4-значному ПИН-коду (Без звонков и SMS)
* **Алгоритм генерации:**
  * Детерминированная криптографическая функция `getClientPin(phone, clientId)` на базе `HMAC-SHA256(JWT_SECRET, cleanPhone)`.
  * Возвращает постоянный 4-значный код (1000..9999). Не требует внешних SMS-шлюзов и миграций базы данных.
* **Эндпоинт:** `POST /api/client/auth/pin`
  * Защищён строгим рейт-лимитером `limiterPinAuth` (макс. 10 попыток за 15 минут).
  * При совпадении ПИНа генерирует сессионный токен.
* **CRM мастера:** ПИН отображается в бейджах карточек списка клиентов и в деталях клиента (`PIN: 4821`) с кнопкой копирования.
* **Личный кабинет (`profile.html`):** Форма ввода телефона с маской и 4-значного ПИН-кода с подсказкой *«ПИН-код указан в заказ-наряде или у мастера»*.

### Архитектура сохранения порядка каталога услуг и отзывов (sort_order)

* **Проблема:** При редактировании услуги в CRM запись перемещалась в конец списка. Причина кроется в двух факторах:
  1. В Supabase у всех услуг изначально было значение `sort_order: 0`.
  2. В PostgreSQL при выполнении `UPSERT`/`UPDATE` создаётся новая версия строки в конце физических страниц таблицы (MVCC). При `ORDER BY sort_order` строки с одинаковым значением сортируются по порядку физического размещения на диске, из-за чего обновлённая строка всегда оказывалась последней.
* **Решение:**
  1. **Нормализация данных:** Всем услугам присвоен уникальный последовательный `sort_order` (0, 1, 2, 3...).
  2. **Детерминированная вторичная сортировка:** Во все эндпоинты выборки (`/api/data`, `/api/services`, `/api/services/reorder`, `/api/reviews/reorder`) добавлен вторичный ключ `.order('id', { ascending: true })`.
  3. **Сохранение порядка на бэкенде (`POST /api/services`):**
     * При обновлении услуги, если `sort_order` не передан явно, он считывается из существующей записи в БД.
     * При добавлении новой услуги она автоматически получает `sort_order = max(sort_order) + 1` (добавляется в конец, не конфликтуя с первыми элементами).
  4. **Синхронизация состояния на фронтенде (`public/js/admin.js`):**
     * `openServiceModal` считывает сохранённый `s.sort_order` в скрытый инпут.
     * `window.onDrop` и `window.toggleService` обновляют `DATA.services` свежим массивом из ответа сервера `res.services`.

## 🛡️ Архитектура: Карточка сотрудника и многоуровневая безопасность аккаунтов (v1.4.1)

### 1. Контекст и бизнес-требования
По мере масштабирования сервиса (расширение штата мастеров, добавление учеников/подмастерьев, диспетчеров/менеджеров клиентского сервиса, руководящего звена) возникла необходимость:
1. Перехода от обезличенного глобального имени мастера в настройках к персональным, подробным карточкам каждого сотрудника.
2. Гарантировать строгую безопасность учетных записей, исключить узурпацию прав, случайное или намеренное удаление ключевых аккаунтов, понижение в правах руководителей проекта (`lead`, `chief`).
3. Предоставить безопасный механизм смены паролей (bcrypt 10 раундов) и привязки Telegram-ботов для оперативных уведомлений.

### 2. Модель ролей и прав доступа (RBAC)
В системе определены 5 должностных ролей:
* `lead` — **CEO / Руководитель проекта** (полный доступ, управление сотрудниками и финансами). Защищённый системный аккаунт.
* `chief` — **Главный автоэлектрик / Проект Лид** (технический контроль, управление сменами, заявками и мастерами). Защищённый системный аккаунт.
* `master` — **Мастер-автоэлектрик** (работа с клиентами, оформление ремонтов, получение уведомлений).
* `apprentice` — **Подмастерье / Помощник** (диагностика, вспомогательные работы под кураторством).
* `manager` — **Клиентский сервис / Менеджер** (приём входящих заявок, коммуникация, сервисные напоминания).

### 3. Защита системных аккаунтов (Security Core)
Ключевые системные аккаунты проекта:
* **Sid Vicious:** ID `19e4e551-4454-4710-8a6d-a4effc211201`, логин `vk_1125744855`, роль `lead`.
* **Seryozhka Abisonov:** ID `41dbea03-a28c-4d1e-bbf0-be86737301b5`, логин `vk_250130315`, роль `chief`.

**Механизмы защиты на бэкенде (`api/index.js`):**
1. **Защита от удаления (`Immunity from Deletion`):**
   - Константы `PROTECTED_MASTER_IDS` и `PROTECTED_MASTER_USERNAMES`.
   - При попытке `DELETE /api/masters/:id` для защищенного аккаунта бэкенд прерывает запрос с кодом HTTP 403 Forbidden и логирует `[SECURITY ALERT]`.
   - Защита от самоудаления: любой сотрудник блокируется от удаления своего собственного аккаунта (`cannot_delete_self`).
2. **Защита от понижения роли (`Demotion Block`):**
   - При `PUT /api/masters/:id` системные роли `lead` и `chief` принудительно восстанавливаются на сервере. Обычные пользователи не могут сменить роль защищённого аккаунта.
3. **Защита системного логина (`Username Lock`):**
   - Для защищенных аккаунтов смена `username` заблокирована на сервере и клиенте.
   - Запрещена регистрация новых аккаунтов с логинами из списка `PROTECTED_MASTER_USERNAMES`.
4. **Ограничение прав на создание/удаление (`Privilege Gate`):**
   - Только пользователи с ролями `lead` или `chief` (функция `isPrivilegedMaster(master)`) имеют право регистрировать новых сотрудников (`POST /api/masters`) и удалять сторонние аккаунты (`DELETE /api/masters/:id`).
5. **Безопасная смена пароля и JWT Refresh:**
   - Пароли валидируются на длину (не менее 6 символов) и хэшируются через `bcrypt.hashSync(pwd, 10)`.
   - Если пользователь меняет пароль самому себе, сервер автоматически возвращает свежий `token` с обновленными claims, предотвращая разлогин.

### 4. Структура и потоки данных (Data Architecture)
* **Таблица Supabase `masters`:**
  - Поля: `id` (UUID), `name`, `username`, `password` (хэш), `telegram_chat_id`, `created_at`.
* **JSONB Метаданные `settings.data.masters_meta`:**
  - Для обеспечения гибкости и исключения опасных миграций DDL расширенные атрибуты профиля хранятся в ключе `masters_meta[masterId]`:
    ```json

          "role": "lead",
          "phone": "+7 (959) 000-00-01",
    ```

  - При выборке `GET /api/masters` бэкенд объединяет данные таблицы `masters` с объектом `masters_meta[id]`, а также выставляет флаг `isProtected: true/false`.
  - При удалении мастера связанная запись в `masters_meta` автоматически очищается.
